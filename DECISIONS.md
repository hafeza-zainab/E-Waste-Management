# Decisions and assumptions

| # | Decision | Why |
|---|----------|-----|
| 1 | Separate git repo created inside the project folder (`git init -b main`). | The parent directory is a git repo covering the whole home directory; nesting keeps hackathon history clean. |
| 2 | Next.js 16 with `cacheComponents` and `partialPrefetching` turned **off**. | Every page reads per-request state (session cookie, SQLite). Classic dynamic rendering avoids wrapping every read in Suspense. |
| 3 | Prisma pinned to v6. | v7 requires driver adapters and a config file; v6 keeps `npm run setup` simple for judges. |
| 4 | `.npmrc` sets `legacy-peer-deps=true`. | npm 10 crashes (`edgesOut` arborist bug) resolving vitest's optional peers. |
| 5 | shadcn-style components are hand-written in `components/ui` (cva + tailwind-merge) with a `components.json`. | The shadcn CLI is interactive and assumes a PostCSS Tailwind setup; this scaffold uses the Turbopack Tailwind loader. |
| 6 | Statuses and types are strings validated in TypeScript/zod, not DB enums. | Prisma does not support enums on SQLite. |
| 7 | Money is stored as integer cents everywhere. | Avoids float drift in fee/payout maths. |
| 8 | Platform fee applies to the whole job total (default 10%, `PLATFORM_FEE_BPS`). | Simple, visible, testable. |
| 9 | Role switcher is a plain httpOnly cookie, no authentication. | Per brief; demo only. |
| 10 | Landing-page scenario buttons open `/owner/new?scenario=...`, which prefills the intake form. | Fast, scripted demo entry. |
| 11 | Default model is `claude-opus-5-5` (one constant in `lib/ai/config.ts`, overridable with `ANTHROPIC_MODEL`). | Current recommended model per Anthropic docs. Cheaper models can be swapped in with the env var. |
| 12 | Environmental impact is computed in code from `lib/impact`, never by the model. | Transparent, auditable, testable. |
| 13 | Demo mode = `DEMO_MODE != "false"` OR no `ANTHROPIC_API_KEY`. | Judges never hit a missing-key error. |
| 14 | The swollen-battery fixture simulates a model wrongly suggesting `diy`; the code gate overrides it to `technician`. | Makes the code-level safety gate visible in the demo. Real-mode output is never altered except by the gate. |
| 15 | Demo-mode free-text cases are keyword-matched to a scripted scenario, else get a clearly labelled generic fixture. | The app stays usable without a key but never pretends to be a real diagnosis. |
| 16 | DIY guide route re-checks `diy_allowed` on read, and `generateGuide` refuses when it is false. | Defence in depth for the safety rule. |
| 17 | Uploads are identified by magic bytes, limited to 4 MB, saved to `public/uploads` with random names. | Never trust client MIME type or filename. Files are ephemeral on Render free tier. |
| 18 | Booking/quote CTAs for technician, donate and recycle paths are intentionally absent until Phases 3, 5 and 6. | No fake buttons. |
| 19 | PayPal base URL is hard-coded to `api-m.sandbox.paypal.com`. | The app can never touch live money. |
| 20 | Checkout uses intent `AUTHORIZE`: funds are held at approval and captured only on verified completion (Phase 4). | Matches the "release only after verified repair" promise without a platform balance. Sandbox authorizations last 29 days. |
| 21 | Without PayPal credentials the app runs a clearly labelled local simulation (`SIM-` ids, same server flow, banner says so). | Judges can run the full flow with no keys. |
| 22 | Order amount is always read from the stored quote in the DB; the browser only sends a job id. The authorize route checks the order id belongs to the job. | Prevents amount tampering and cross-job authorization. |
| 23 | PayPal-Request-Id is deterministic per job/order (`reloop-order-<job>`, `reloop-authorize-<order>`); state changes are conditional transitions (`updateMany where status = from`); webhook event ids are unique. | Retries, double clicks and webhook replays are harmless. |
| 24 | Webhook route verifies signatures with PayPal's verify-webhook-signature API and only trusts `*.paypal.com` cert URLs. A dev-only `/api/paypal/webhook/simulate` replays the same handler without a signature. | Safe by default, testable locally. Simulate route is 404 in production unless PayPal is simulated. |
| 26 | Order creation uses a **fresh PayPal-Request-Id per attempt** (was deterministic per job). | A deterministic id returned the same, possibly stuck, order after a failed approval, so retries could never succeed. Double-click safety now comes from the job storing the latest order id and the authorize route rejecting any other. |
| 27 | Orders use `payment_source.paypal.experience_context` (not the deprecated `application_context`), all items are `DIGITAL_GOODS`, zero-value items are dropped. | Current PayPal field; a service with `NO_SHIPPING` should not carry `PHYSICAL_GOODS` lines. |
| 28 | The SDK client id is always the server's `PAYPAL_CLIENT_ID`; `NEXT_PUBLIC_PAYPAL_CLIENT_ID` is ignored. | A browser/server app mismatch is a classic `genericError` cause; one source removes the class of bug. |
| 29 | Full-page redirect flow ("Continue to PayPal in this tab") returns to `/jobs/[id]/return`, which authorizes server-side. Popup errors are POSTed to `/api/paypal/client-error` (debug id logged). | Works when popups or tracking prevention break the SDK. |
| 30 | **Dev-only "Simulate buyer approval"** (`NODE_ENV != production` AND `PAYPAL_SIMULATE_APPROVAL=true`). Stores `authSimulated=true`, tagged SIMULATED everywhere; capture and payout for it are also simulated (never a real PayPal call). | Unblocks development without hiding the sandbox problem. **Shipping requirement: a real sandbox authorization, capture and payout must be demonstrated end to end before submission.** |
| 31 | One transition table (`lib/jobs/state-machine.ts`) lists every legal `(from, to, actor)`; every state change goes through `transitionJob`, a conditional `updateMany`. Who may trigger each action is enforced in `lib/jobs/permissions.ts` using the session principal, never form fields. | Illegal moves and wrong actors are impossible server-side, not just hidden. The cookie "session" is still demo-grade, not real authentication. |
| 32 | Capture happens only in `confirmRepair`, with `PayPal-Request-Id = reloop-capture-<jobId>` and a stored `captureId`. Payout only runs with a stored capture. | Exactly-once capture; no payout without money in hand. |
| 33 | Authorization timing: 3-day honor period, valid 29 days. After day 3 we call re-authorize before capture (if PayPal refuses we still try the original); past day 29, or when PayPal says voided/expired, the job becomes `authorization_expired` and nothing is charged. | PayPal Payments v2 behaviour as documented; the docs site could not be re-fetched during this session, so verify these numbers against the live docs before submission. |
| 34 | Payouts use `sender_batch_id = reloop-payout-<jobId>[-r<n>]`; `n` increases only after PayPal reports an item failed/returned. A duplicate-batch rejection is treated as "already submitted". Payouts 401/403 (not enabled) records a labelled `simulated` payout with the reason. | A retry can never pay twice, and a genuinely failed item can be re-sent under a new id. |
| 35 | The owner's "Report a problem" sets a flag that blocks capture; the technician clears it by uploading new proof. | Gives the owner a safe exit without a dispute system. |
| 36 | Odd-cent fee maths: `fee = floor((total * bps + 5000) / 10000)` (half-up, integer only); technician gets the remainder. | $0.99 -> fee 10c / payout 89c; $33.33 -> fee 333c / payout 3000c. |
| 37 | Donations use Orders v2 `intent: CAPTURE`, created and captured server-side from validated integer cents (`lib/donations`). The `/donate` page loads the SDK with `intent=capture` and its own `dataNamespace` (`paypal_donate`), so it never shares a script instance with the job pages (`intent=authorize`). | The two intents must not be mixed in one SDK instance. |
| 38 | Each donation attempt is its own row (`created`), with a fresh order `PayPal-Request-Id`; capture is claimed with a conditional `created -> capturing` update and uses `PayPal-Request-Id = reloop-donation-capture-<publicId>`. Only `completed` rows are counted or shown. | Capture exactly once; abandoned attempts are harmless. |
| 39 | Donations have three modes like jobs: real sandbox, redirect fallback (`/donate/return`), dev-only simulated approval (`PAYPAL_SIMULATE_APPROVAL=true`, never in production). With no PayPal credentials: simulated outside production, **switched off in production** (not faked). | Honors "simulated must never be reachable in production". Note this differs from jobs, where the no-credentials simulation (decision 21) still runs in production with a visible banner. |
| 40 | Donation pages and certificates are reachable only by an unguessable UUID `publicId` (not the row id). The certificate exists only for `completed` donations. Public lists show first names only and no PayPal ids. | No donor accounts exist; an unguessable link is the access control. |
| 41 | "Devices funded" = floor(amount / $25). The $25 refurbish subsidy and the $1,000 goal are illustrative placeholders in `lib/impact/constants.ts`. The beneficiary and the recycler are labelled demo placeholders. | No invented organisations; no tax claims. |
| 42 | **No impact constant has a verified source.** All are labelled "illustrative estimate" in code and on `/impact`. I removed the earlier comment claiming they came from public LCA literature, which I could not confirm. | Do not invent citations. |
| 43 | `ImpactEvent.deviceId` is unique, so a device is counted once. Repairs are recorded when a payout is released (flagged demo if simulated); recycling when a pickup is processed. Seeded rows are flagged demo; `/impact` footnotes demo data. | Matches "counted once per device". |
| 44 | Recycling "collected/processed" buttons are a demo stand-in for the recycler and exist only when `NODE_ENV != production`. | Simulated actions must not be reachable in production. Consequence: on the hosted demo a booked pickup stays "booked". |
| 45 | `qrcode` is listed in `serverExternalPackages`. | Turbopack bundling of its Node entry crashed the CV route (HTTP 500) in dev. |
| 46 | Demo-only controls (recycler "Demo control" buttons) are gated by an explicit `DEMO_ACTIONS=true`, not by `NODE_ENV`. | The hosted demo runs in production mode and still needs them; there is no real recycler. |
| 47 | A demo scenario locks the device type/brand/model/age on the server (and read-only in the form), whatever the browser sends. The agent's scripted runs do the same. | Browser autofill or edits can no longer make the job page show a different device than the diagnosis. |
| 48 | Agent = Claude tool-use loop, max 10 executed tool calls, 90 s deadline, user Stop aborts. All tools are deterministic server code behind one `executeTool` that zod-validates arguments from any caller. | Bounded cost and time; malformed model output cannot crash a run. |
| 49 | **Human-in-the-loop is enforced in code.** `create_paypal_order` is registered but never offered to the model and refused if requested. `request_user_approval` only creates an *un-approved* `AgentApproval` bound to job id, total cents and a SHA-256 of the line items (15 min). Only `POST /api/agent/approve` (session must be the job's owner) sets `userApprovedAt` and mints single-use tokens (only hashes stored). `POST /api/paypal/orders` demands a valid token for any job with an `agentRunId`. | There is no code path where a run alone creates an order. Deviation from the brief: the approval tool returns an approval *request id*, not a usable token; the token is minted by the user's click, so the model never sees one. |
| 50 | Tokens are single use per PayPal order creation; each PayPal button press or "continue in this tab" re-mints one while the approval is unexpired and the quote unchanged. | Popup failures and retries still work without a reusable secret. |
| 51 | Budget comes from the UI field or is parsed from the goal; it is stored in the run context and is not a tool argument. `build_quote` returns a blocked result (no job) when over budget and lists verifiable alternatives. The user can raise it only through the UI ("Raise my budget … and re-run"). | The model cannot talk its way past the cap. |
| 52 | Even the dev "Simulate buyer approval" refuses agent jobs until the user has clicked Approve. | Keeps the approval rule uniform. |
| 53 | Scripted demo runs (no key, `DEMO_MODE`) call the same tools through the same executor; only the choice of next tool is scripted. UI labels them "Scripted demo run". | Not a fake UI: the quote, job, approval and budget checks are real. |
| 54 | **PayPal Agent Toolkit not adopted.** Its docs (README, 45-minute timebox) do not document `intent`, `custom_id`, `experience_context` or return-URL parameters for `create_order`, so I could not confirm it can create our `AUTHORIZE` order with NO_SHIPPING and per-job request ids. It would also add an LLM-reachable payments surface that must be filtered (`configuration.actions.orders.create`) to respect the approval rule. Our REST wrapper is already verified against the sandbox. Revisit if the toolkit documents those fields. | Smallest, auditable payment surface. |
| 55 | Agent runs are persisted (`AgentRun.eventsJson`) so `/agent?run=<id>` restores the trace and quote. No per-user rate limiting exists yet, so a live (paid) Claude agent on a public URL could be abused. | Known gap; add limiting before exposing a live-key deployment. |
| 56 | Rate limits are in-memory fixed windows per IP and per `reloop_sid` cookie (set by `proxy.ts`), with tight limits on the agent and diagnosis. Live Claude calls are counted per process per UTC day against `AI_DAILY_CALL_CAP`; beyond it `isDemoMode()` is true and a notice is shown. | Single-instance demo; protects the API bill without infrastructure. Resets on restart. |
| 57 | CSP is static in `next.config.ts` and allows `'unsafe-inline'` scripts plus PayPal hosts. Verified in a real browser that the SDK, popup and redirect reach `sandbox.paypal.com`. | A nonce CSP would force dynamic rendering of every page and complicate the PayPal SDK. |
| 58 | `instrumentation.ts` logs active modes at boot and **force-disables** `PAYPAL_SIMULATE_APPROVAL` in production (instead of crashing). The code paths also check `NODE_ENV` independently. | Defence in depth; a misconfigured deploy stays up but safe. |
| 59 | The seed writes demo data only to an empty database and always refreshes the parts catalogue; `npm run db:reset` wipes. `start:render` runs migrate then seed. | A restarted host keeps user-created data and never wipes it by accident. |
| 60 | Uploads are served by a route handler (`app/uploads/[name]`) with a strict uuid.ext filter; the UI degrades when a file is gone. | Next serves only build-time `public/` files in production; the free host's disk is ephemeral. |
| 61 | Logs are one-line JSON through `lib/log.ts`, which drops secret/PII-looking keys, scrubs emails and long tokens, and keeps PayPal `debug_id`. | Debuggable without leaking. |
| 62 | `--muted` darkened to `#4a6562` and a test enforces WCAG AA contrast for the theme pairs. Server-action results (`?ok=`/`?error=`) are shown as toasts on job, technician, donate and diagnosis pages; form pages keep inline errors. | Accessibility and clearer feedback. |
| 63 | Browser checks use `playwright-core` with the system Edge/Chrome plus `axe-core`, not a downloaded browser (`npm run verify:ui`). Lighthouse was attempted and produced no result, so no Lighthouse scores are claimed. | Works on Windows without a large download. |
| 25 | Platform fee is deducted from the technician's share, shown on the quote. The customer pays exactly the quoted total. | Transparent for both sides. |
| 64 | **Guided demo tour** drives the real UI (data-tour targets, synthetic clicks) and never calls PayPal. Tour records carry `isTour`/`tourRunId`; a `TourRun` row + httpOnly cookie is the session; money on tour jobs is `SIM-TOUR-*` / `TOUR-SIMULATED` computed locally. | Judges see the full flow in about 3 minutes without PayPal sandbox friction, and captions cannot drift from the product. |
| 65 | **Why this does not weaken the production rule on simulated approvals:** `PAYPAL_SIMULATE_APPROVAL` is untouched and still forced off in production. The tour never sets `authSimulated` through that path: `/api/tour/pay` only accepts a job tagged `isTour` that belongs to the caller's own tour session, only when `DEMO_ACTIONS=true`, only after the user's real Approve click, and the lifecycle refuses every other action on a tour job without that session. A non-tour job can never become TOUR-SIMULATED, and a tour job can never reach PayPal (three guard layers) or any public total (excluded in every query and never given a VerifiedRepair/ImpactEvent). | The tour is a labelled, isolated, self-deleting demo, not a bypass of payment rules. |
| 66 | Tour cleanup: Finish, Stop, next page load after an interrupted run (stale heartbeat or lost state + flag cookie), and a server purge of runs older than 2 hours and orphaned tour records when a new tour starts. A reload within 20 s resumes the run at the start of its chapter. | CampusSync left leftovers after a mid-tour reload; every exit path here removes the data. |
| 67 | Tour agent runs use their own rate-limit bucket (`tourAgent`, 8 per 10 minutes) so repeated tours do not exhaust the public agent limit, and are bounded by the `tour` limiter on start/pay/cleanup. | Judges may run the tour several times. |
| 68 | **Real accounts replace the role switcher** (`User` + `Session`, with the existing `Owner` / `Technician` rows kept as role profiles). | The lifecycle rules, quotes and approvals already key on Owner and Technician ids, so linking a user to a profile changes who may act without touching any money, safety or approval rule. The role cookie is removed. |
| 69 | **Custom auth with Node built-ins** (`crypto.scrypt`, random session tokens stored as SHA-256, Origin checks in `proxy.ts`). No auth library. | Nothing heavy to add or audit for a sandbox demo, nothing to keep patched, and every rule (hashing parameters, rotation, expiry, CSRF, redirect safety) is a small function with tests. The trade-off is that features like email verification and password reset are not there, and that is documented. |
| 70 | **Guest mode: "Continue as guest (demo)" creates a real `User` with `isGuest=true`.** Purged after 24 hours. | Judges must not be forced to sign up. A real user with a normal session keeps one identity model, so every feature and every authorization check works the same for guests, with no special cases to get wrong. |
| 71 | **The guided demo uses a separate identity overlay** (`reloop_tour_role` cookie bound to the tour run id; tour records belong to a dedicated tour owner), not the visitor's session. | The tour needs to act as an owner and a technician. Switching the real session would log a visitor out, rotate or replace their cookie, and show their own data in the tour. The overlay authorizes only records tagged with its run, and the real cookie is never touched, so the home-page demo can leave a logged-in user, a guest or a logged-out visitor exactly as they were. |
| 72 | **Two entry points, one tour.** The tour state carries `returnTo` (`/` or `/signup`) and `preserveSession`. The signup entry adds an "Accounts" chapter that only points and talks. Both entries clean up and navigate to `returnTo` on finish and on Stop. | The signup page should explain the two roles without ever filling in or submitting the real form or creating a user. |
| 73 | Passwords: scrypt N=16384 (about 16 MB, tens of milliseconds) rather than a heavier setting. | Fits free-tier hosting and keeps the tests and the login rate limit usable; the parameters are stored per hash and can be raised later without a migration. |
| 74 | Signup says when an email is taken; login never does. | A friendly signup error is worth more than hiding that an email exists in a sandbox demo. Login stays generic and is rate limited per IP and per email. |
